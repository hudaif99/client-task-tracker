## Important behavior to preserve

- Client deletion with no tasks uses normal confirmation. With tasks, DELETE first returns 409 CLIENT_TASKS_CONFIRMATION_REQUIRED and taskCount without deletion. The page shows an extra warning and requires a separate Delete client and tasks click.
- Confirmed DELETE JSON: {"confirmTaskDeletion":true,"expectedTaskCount":2}. The backend locks the client FOR UPDATE, counts tasks, and deletes on the same pooled connection and transaction. A changed count requires fresh confirmation. The parent lock blocks new FK references until completion. PostgreSQL cascades deletion atomically.
- Do not change cascade to restriction: user explicitly rejected deleting tasks individually.
- IDs are canonical positive decimal integers in PostgreSQL integer range. JSON bodies are limited to 2 KB. Names/titles are trimmed and Unicode character limits checked; null characters rejected.
- Successful writes validate response shape and matching resource IDs/status before refreshing. Recoverable rejections preserve drafts. Uncertain results preserve/lock input and offer explicit recovery, never automatic write retry. Prevent duplicate clicks immediately with refs.
- Task PATCH filters by BOTH task ID and client ID. The server reads title and/or status; IDs come from the URL. Supplied fields are validated together before one UPDATE, omitted fields keep their saved values, and explicit null is rejected. Status changes assign pending/completed explicitly rather than toggling in SQL. Concurrent edits to the same field use the last saved value.
- Session-based individual ownership is enforced in Express; no shared tenancy model or RLS has been introduced.
